# Gap Audit — Phase 1 sync envelope migration

Scope: full P2P message-type inventory (every `sendP2P` call site and every
`handleP2PMessage`/monkey-patch receiver) → migration to namespaced
`domain:action` Gates on a dedicated `syncStream` → X25519 + AES-256-GCM
wiring → jsdom + real-HTTP-server verification (same method as
`GAP-AUDIT-2026-07-15.md`) → targeted fix verification. See
`04-PHASEMAP.md` Phase 1 for the full narrative; this file is the
audit-trail version of the same findings.

## Fixed

**Three sequential `window.handleP2PMessage` monkey-patches silently
shadowed each other.** The last-defined wrapper intercepted
`'love'`/`'feeling'`/`'need'`-shaped types via a `type.startsWith('msg_')
|| [...].includes(type)` check and returned before falling through, so
the original handler's `'love'` and `'feeling'` branches could never run
for those types. Confirmed two live casualties:
- `syncFeelingToPartner()` (feeling-wheel save path) sent `feeling_update`
  — a type no gate, flat or namespaced, ever listened for. Converged with
  the Guided Feeling Flow's save path onto one gate, `feeling:set`.
- `sendLove()` (Settings → System → "💌 Send Love") checked
  `window._dc`/`window._bc`, two globals nothing in the codebase ever
  assigned — always showed "Connect to Raven first" regardless of actual
  connection state. Rewired onto the real pipeline as `love:sent`.

**`sendSafetyRequest()` unconditionally queued to the outbox even on a
successful send** — `sendP2P(payload); ErosPipeline.push(payload);` with
no success check, guaranteeing a duplicate resend on the next reconnect.
Now uses `emitSync()`, which only queues on actual failure.

**Fix** (in `shared/eravos-kernel.js`): replaced the monolithic
`handleP2PMessage` if/else chain and all three monkey-patch layers with
25 discrete `syncStream.register(new (class extends Gate {...}))` gates,
one per `domain:action` type, plus `emitSync(type, data)` /
`dispatchSync(envelope)` helpers. `Stream.register()` already throws on a
duplicate signature (it did before this migration too — this just
actually uses that guarantee for the P2P layer instead of a chain of
mutable `window.handleP2PMessage` reassignments).

**E2E encryption was claimed in UI copy, absent in code.** `sendP2P()`'s
own comment said "Prefer encrypted mesh channel" while sending everything
in the clear. Fixed for real: new `shared/eravos-crypto.js` (X25519 RFC
7748 Montgomery ladder + AES-256-GCM via `SubtleCrypto`), wired into the
`presence:hello` handshake and `sendP2P()`. Honest scope limitation
stated in the module itself: static identity keys, no forward secrecy.

## Checked, no action needed

- All 25 syncStream gate signatures + 5 appStream gate signatures:
  zero collisions (`grep` of every `super('...')` registration, one
  occurrence each).
- Full 36-tab click-through (jsdom + `python3 -m http.server`, mirroring
  `GAP-AUDIT-2026-07-15.md`'s method): 25 real tabs + 4 settings subtabs +
  the 7 already-documented unbuilt `sc-*` Community stubs (still
  correctly failing with HTTP 404 — pre-existing, named, out of scope).
  Zero window errors, zero newly-thrown errors.
- Simulated incoming `feeling:set` envelope → `partner-feeling-display`
  updates correctly. Duplicate gate registration → throws immediately.
  Unclaimed type (`'totally:unknown'`) → lands in `syncStream.pending`,
  no throw.
- X25519 implementation cross-validated against `@noble/curves` across 20
  random keypairs (public-key derivation + ECDH agreement both match).
  AES-256-GCM encrypt/decrypt round-trip verified; a tampered ciphertext
  byte correctly fails GCM auth instead of silently decrypting garbage.
- Real `setupPeerConn`/`sendP2P` code path exercised via a mocked
  connection (not a reimplementation): identity keypair created on
  connect, `presence:hello`/`sync:manifest` envelopes sent with correct
  shape, zero thrown errors.

## Named, not fixed (out of scope this pass)

- **"One-Way Message" has no compose-side toggle.** Cataloged as a
  feature (manifest/config lists it), and the *receiving* side is ready
  (`subtype === 'one_way'` in the `message:sent` gate), but nothing in the
  compose UI ever sets that subtype. Still a gap, not a bug — there's no
  sending half to have broken.
- **`fallbackP2PConnect`'s BroadcastChannel has no sender.**
  `window._fallbackBC` is assigned and given a receive listener; nothing
  in `sendP2P`/`_rawSend` ever posts to it. Same-device debug fallback
  only (used when the PeerJS library itself fails to load) — not the
  partner-sync critical path Phase 1's exit criteria cover.
- **No forward secrecy in the new encryption layer.** Static X25519
  identity keys per role; the derived AES key doesn't rotate per session.
  Named in `shared/eravos-crypto.js`'s own header comment and in
  `04-PHASEMAP.md`.

## Method

Same as `GAP-AUDIT-2026-07-15.md`: `node --check` on every changed file ·
jsdom + native `fetch`/`crypto.subtle` polyfills against a live
`python3 -m http.server` instance · full DOM event simulation (tab
mounts, mocked P2P connections) rather than static analysis alone ·
targeted before/after tests on each fixed function, confirming actual
state changes (DOM text content, thrown/not-thrown, queue contents), not
just absence of console errors · an independent third-party crypto
library (`@noble/curves`) used as a correctness oracle for the new X25519
implementation rather than trusting hand-derived test vectors (an earlier
attempt to use transcribed RFC 7748 test vectors from memory produced a
false failure from a transcription error, not an implementation bug —
caught by cross-validating against random keypairs instead of trusting
the transcription).
